# Переработка: план и решения

## План

1. Подтвердить границы Alloha и выбрать транспорт управления. В работе: текущий public postMessage API содержит только play/pause/seek/duration/getTimeSave. Запрошен выбор пользователя между собственным плеером с проверенным потоком и сохранением iframe с честными ограничениями. Пользователь выбрал вариант 1: исследовать собственный плеер с проверенным прямым потоком. См. DIRECT-SOURCE.md.
2. Два варианта интерфейса: компактная полоса участников под видео либо боковая панель. Рекомендация — полоса под видео: одинаковая иерархия на телефоне и компьютере, основное управление остаётся в единственном плеере. Подготовить локальный переключаемый макет обоих вариантов.
3. Автоматическая синхронизация на реальной телеметрии выбранного адаптера. Старые анонимные комнаты v2 совместимы; новая авторизованная комната связывается с контекстом пользователей.
4. Аккаунты и API: реализуются независимо от выбора плеера. Пароли scrypt, HttpOnly-сессии, CSRF, код восстановления без выдуманной почты. Внешний Basic/viewer-периметр не меняется.
5. UI аккаунта: вход/регистрация/восстановление, одноразовый показ recovery-кода, приглашение в пару, история «Один» / «Вместе», явный импорт локального прогресса.
6. Сквозные проверки, ревью, реальные измерения; недоступные проверки явно перечислить. Коммит и деплой отдельно.

## Данные и согласование

- Пользователь ≠ устройство/сессия ≠ комната. Учётная сессия хранит хеш случайного токена. Идентичность вкладки ведущего остаётся отдельной арендой.
- Контекст — стабильный хеш отсортированных уникальных user ID. Личный контекст содержит одного человека. Пара/группа — отдельный состав с явным согласием каждого; новый состав создаёт новый контекст.
- Комната временная, прогресс переживает её закрытие. Ключ checkpoint: контекст + тайтл + сезон + серия + версия видео.
- Личный checkpoint — compare-and-swap по revision и идемпотентный operation_id. Старый offline-отчёт не переписывает новую запись; конфликт выводится пользователю, автоматического присвоения последней версии для повторной записи нет.
- Совместный checkpoint пишет только действующая комната с арендой контекста. Клиентский POST не может записать общую историю напрямую. При двух активных комнатах одного состава вторая получает конфликт, пока первая не отпустит аренду.
- Личная и совместная позиции никогда не копируются автоматически друг в друга. При продолжении одному с текущей позиции пользователь явно выбирает это; прежняя личная позиция предлагается отдельно.
- Общая история сохраняется только после подтверждённого совместного воспроизведения; ожидание не считается просмотренным временем. Поздний участник не получает прошлую историю другого состава.
- Скрытие общей истории действует только для текущего пользователя. Удаление аккаунта анонимизирует имя для партнёра и сохраняет его общий checkpoint; личные checkpoints/сессии удаляются.
- Старые глобальные catalog-progress не принадлежат первому зарегистрировавшемуся. Импорт локальных данных — отдельное явное действие только в личный контекст, с проверкой версий и без перезаписи существующих записей.

## Ревью архитектуры до UI

HIGH: остановку timeupdate нельзя считать canplay; без поддерживаемого адаптера автоматический wait-for-all не доказан. Решение — не прятать старый probing за новым дизайном; подтвердить возможности выбранного транспорта.
HIGH: прозрачный слой над всем Alloha лишает гостя разрешённых настроек. Не использовать как решение выборочных прав.
HIGH: общий анонимный progress нельзя автоматически раздать аккаунтам. Новые таблицы изолированы; только явный импорт личной локальной истории.
HIGH: конфликт параллельных устройств/комнат может затирать позицию. CAS и аренда общей записи обязательны, проверяются тестами.
MEDIUM: автоматический reload при обновлении service worker перезапускает плеер. Убрать безусловный reload, обновление применять при следующем открытии/явном действии.
MEDIUM: откат кода не должен требовать удаления новых таблиц или данных. Миграция аддитивная; старый код просто не использует таблицы аккаунтов.

## Статус

- Диалог аккаунта на сайте: регистрация/вход/восстановление, приглашение в пару, фильтр истории, скрытие только своей истории. Метаданные истории загружаются с параллелизмом 4.

- Протокол комнат 3 на сервере проверяет серверную личность аккаунта, согласие на join, владельца роли ведущего. Формирует общий контекст и пишет checkpoint только при свежем подтверждении участников. Старый протокол 2 сохранён для совместимости. - `/watch-preview.html`: самостоятельный кликабельный макет двух компоновок, ролей и основных состояний. Это демонстрация интерфейса, не действующий новый плеер.

Проверено:

- 8 JS-тестов старой модели комнаты и home-discovery проходят. Они не доказывают исправление жалоб на реальном Alloha.

- В браузере на локальном 8095: регистрация тестового аккаунта, выдача кода, экран аккаунта. Пароли и код относятся только к одноразовой локальной QA-базе.

Не завершено / не выдавать за готовое:
- API iframe Alloha не даёт buffered/canplay и выборочное отключение pause/seek при сохранении качества/звука. Ожидается решение пользователя о способе воспроизведения; запрос отправлен в чате. Переход на собственный плеер и прямой поток не согласован и не реализован.
- Ручная подготовка в старом контроллере всё ещё существует. Новая синхронизация, адаптер и защита управления зрителя не реализованы.
- Фронтенд ещё не использует аккаунтный протокол комнат 3; совместное продолжение из истории показывает явное объяснение, а не незаметно запускает личный просмотр.
- После «Продолжить одному» аккаунтная запись не начинается автоматически: требуется явный выбор политики сохранения прежней личной точки. Это безопасный незавершённый сценарий.
- Нужны обработка конфликтов с выбором позиции, продление/отзыв устройств, политика хранения событий и миграционные/нагрузочные проверки.
- Нет сквозной проверки окончательного плеера, реального телефона, смены качества/VPN и непрерывного 10–15-минутного замера.
- Коммит, push и деплой не выполнялись.

## Замечания к макетам

1. Панель под видео рекомендована: сохраняет ширину кадра и естественный порядок чтения на телефоне. Боковая удобна для длинного списка участников на широком экране, но сужает фильм; на телефоне сворачивается под видео.
2. Выход виден всегда, завершение скрыто в меню ведущего. Зрителю не предлагаются недоступные общие действия.
3. Таймкоды отделены от live-status; обновления секунд не озвучиваются как уведомления. При отсутствии связи точность не выдумывается.
4. Выбор роли/состояния — инструменты макета, в продуктовый плеер не переносятся.
5. Это ограниченное сценарное ревью. Полное ревью шести доменов better-interface и реальных локальных настроек ещё не выполнено; текст «Громкость/Качество/Полный экран» в макете пока является подписью, а не рабочими настройками.


## Выбор транспорта — продолжение

Пользователь согласовал исследование собственного плеера. Найден отдельный контракт Alloha `/direct` с `secret_token`; подготовлен изолированный `tools/alloha_direct.py` и 5 модельных тестов. Ключ прямого доступа отсутствует в проверенных настройках. HTTP-маршрут и переключение пользователей на новый источник пока не включены: без ключа нельзя проверить ни ответ реального direct API, ни CORS/сегменты/истечение ссылок на двух устройствах. Это ограничение доступа, а не завершённая интеграция. Подробности: `DIRECT-SOURCE.md`.

## Текущее решение: iframe с согласованными ограничениями

Пользователь выбрал **оставить iframe Alloha**. Требования о строгой блокировке pause/seek у гостя и подтверждённом автоматическом ожидании буфера заменены явно согласованными ограничениями. Исследование /direct отложено; его адаптер не подключён.

Реализовано локально:
- Новый контроллер iframe: без ручной подготовки и без скрытого play/seek/pause probing. Готовность видео не выдумывается; неизвестный буфер не блокирует общую шкалу.
- Единственное управление play/pause/seek ведущего находится внутри Alloha. В панели комнаты — участники, таймкоды, приглашение, выход, меню ведущего и явный возврат зрителя к общей позиции.
- Комната создаётся до запуска. Уже запущенный iframe сохраняется при создании и выходе. Для сериала перед созданием можно явно указать сезон/серию.
- Быстрые seek объединяются за 300мс, программные echo сопоставляются с конкретным действием, а не блокируют все события на несколько секунд. Краткая pause рядом с seek не должна менять play-намерение; реальные особенности порядка событий провайдера всё ещё требуют проверки на устройствах.
- Зритель, изменивший просмотр у себя, временно выходит из следования. Нет цикла принудительного возврата. Кнопка «Вернуться к ведущему» восстанавливает следование; «Продолжить одному» отключает комнату.
- Комнаты сайта теперь создаются с аккаунтным протоколом 3 и sync_mode=iframe; имя берётся с сервера, join требует согласия. Серверная совместная история включена через существующий checkpoint. Восстановление из совместной истории и выбор личного checkpoint после выхода пока не завершены.
- report различает доступность управляющего соединения и давность события видео. Таймкоды не озвучиваются каждую секунду через aria-live. При ручной паузе показывается последняя известная позиция, а не ложное сообщение о буфере.
- Старые комнаты v2 могут перейти в iframe-модель только при join с секретом ведущего. Гость не получает право изменить режим.

Живая локальная проверка (две вкладки одного браузера, разные аккаунты/cookies на localhost и 127.0.0.1):
- «Ночь в музее», настоящий iframe Alloha: создана комната до первого Play.
- Видео ведущего воспроизводилось (duration 6514,23; readyState 4; без MediaError).
- Зритель подтвердил вход и предложение восстановления внутри Alloha. После запуска догнал ведущего; на одном замере DOM-видео — 155,872 и 155,567 секунды. Это единичный замер, не медиана/95-й процентиль.
- Обычная перемотка вперёд клавишей на шкале Alloha распространилась на гостя; оба продолжали играть.
- Обычная пауза ведущего поставила гостя на паузу. Обратная перемотка сохранила паузу: у гостя 149,6 секунды, paused=true.
- После выхода и повторного создания комнаты из играющего фильма внутренний slider id остался allplay-seek-137, видео продолжало идти около 169 секунды. Каталог не перезагрузился.
- На первом входе гостя обнаружена ошибочная трактовка стартовых событий как ручной перемотки. Добавлена отдельная начальная синхронизация; повторная проверка воспроизведения гостя прошла.

Ограничения приёмки: это не два физических устройства, не две сети, не непрерывный 10–15-минутный прогон. В финальных правках формулировки таймкодов/точная позиция play/pause/миграция старого режима покрываются тестами; повторный живой прогон всей матрицы ещё нужен. Не считать качество/VPN/серии проверенными по одному фильму. Прод остаётся на предыдущей версии; коммит/деплой не выполнялись.
