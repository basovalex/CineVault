# Задание: свежий каталог, новинки и полезные рекомендации CineVault

Работай в `/Users/aleksandrbasov/Developer_CineVault`. Прочитай AGENTS.md. Все документы и интерфейс — на русском. Это задание на будущую реализацию после согласования: сейчас пользователь просит продуманный промпт, а не немедленные правки/деплой рекомендаций.

## Цель и жалоба

Пользователь видит, что новые фильмы можно смотреть у провайдера, но в CineVault они не появляются либо не видны среди новинок. Главная должна регулярно показывать недавние релизы и появившиеся для просмотра фильмы, а рекомендации — помогать выбирать, не повторяя бесконечно старые популярные карточки.

Референс — присланные скриншоты Zona от 02.11.2026: отдельные полки «Популярные новинки фильмов», «Добавленные недавно фильмы», «Новые серии», «Популярные сериалы». Перенять ясное различие назначений полок, а не копировать оформление, оценки, контент или предполагать известным внутренний алгоритм Zona. Скриншоты не доказывают фактические даты релизов, наличие прав или доступность каждого источника.

## Сначала диагностика, затем изменения

Не считать фразу «не добавляются» установленной причиной. Для каждого выбранного примера проследить цепочку: есть у источника → получен импортом → записан в JSON/JSONL → вошёл в SQLite-индекс → не скрыт политикой видимости → возвращается API → попадает в кандидаты главной → не исключён ранжированием → отображается в актуальном клиенте/PWA.

Собрать таблицу 10–20 примеров: несколько карточек со скриншотов, подтверждённые недавние доступные релизы, старый фильм, только что добавленный в каталог, будущий анонс, свежий фильм без голосов, сериал со свежей серией, временно недоступный источник. Даты и наличие проверять по текущим источникам; не выдумывать по постеру/году. Для каждой карточки указать ID, источники дат, доступность, место потери и доказательство. Не запускать массовое перепарсивание и проверку воспроизведения всего каталога до выяснения причин.

Локально уже замечено в коде (это не диагноз продового импорта):
- `tools/catalog_index.py`, collection=new: текущий/предыдущий год, порог 100/1000 голосов, постер, описание >=60 символов и confidence>=6.5. Такой фильтр способен скрывать свежий фильм. Низкий рейтинг не делает релиз несвежим.
- `CatalogIndex.discovery()` выбирает popular_rank и накопленные голоса, ограничивает число кандидатов. Новый фильм может вообще не попасть в набор ранжирования.
- `loadRemoteFreshCatalog()` в `app/app.js` берёт по 8 фильмов/сериалов и обрезает перемешанный набор до 8. Проверить назначение, потери кандидатов, порядок и причины исчезновения полки при сетевой ошибке.
- `tools/sync_alloha_catalog.py` хранит allohaAddedAt из provider date; семантику этой даты проверить, не называть её цифровой премьерой без подтверждения.
- `tools/sync_kinopoisk_dev_catalog.py` использует updatedAt/lookback для daily. Изменение описания/постера не равно появлению нового фильма.

Проверить реально включённые systemd timers/services и compose maintenance, последние успешные запуски, exit status, курсоры/пагинацию, лимиты и 429, даты покрытия, пропущенные окна, актуальность каталожного индекса, кеши клиента. Файлы deploy/ сами по себе не доказывают, что задача запущена на сервере. На проде могут быть собственные изменения: сначала read-only аудит, не заменять каталог локальной копией.

## Разделить понятия свежести

Спроектировать и документировать отдельные поля:
- дата мировой/российской премьеры, цифрового релиза, релиза конкретного региона;
- время первого обнаружения карточки CineVault;
- время первого подтверждённого появления возможности просмотра у источника;
- время обновления метаданных;
- дата выхода и появления конкретной серии;
- последняя проверка доступности, источник и уверенность каждого факта.

Не сбрасывать first_seen/first_available при повторном импорте, перестройке индекса или массовом обогащении. Не присваивать всем старым карточкам сегодняшнюю дату. Для старых неизвестных дат хранить unknown/признак миграции; не поднимать их массово в «Недавно добавлено». Поддержать точность даты (год/день/время), часовые пояса, неверные/будущие даты и детерминированные tie-breaker по ID. Календарные правила интерфейса — Asia/Yekaterinburg, абсолютные события — UTC.

Не объединять разные фильмы по похожему названию. Разделять тайтл, фильм/сериал, сезон/серию, озвучку, качество и версию монтажа. Обновление озвучки не создаёт новую карточку или новую премьеру. Семантику available различать: источник заявлен / недавно проверен / воспроизведение подтверждено / временно неизвестно / недоступно. Отсутствие заранее обновлённой прямой ссылки не означает отсутствие iframe Alloha.

## Главная и каталог

Предложить порядок полок:
1. Продолжить просмотр — в контексте аккаунта, личный и совместный прогресс различимы.
2. Новинки, которые уже можно смотреть — по релевантной дате доступного релиза, с честным статусом.
3. Популярные новинки фильмов — свежесть + ограниченный сигнал популярности/доверия; не пожизненные голоса без ограничения возраста.
4. Недавно добавлено — по первому обнаружению/доступности, включая старое кино, с явной подписью, почему оно здесь.
5. Новые серии — по событиям конкретных серий, а не году начала сериала.
6. Для вас / похожее на просмотренное — персонализация, разнообразие и объяснение выбора.

Раздельно работать с фильмами и сериалами, не отрезать новинки произвольным смешиванием по 4 карточки. Полки ведут в полный список с теми же критериями и устойчивой пагинацией. Рейтинг и качество показывать честно; отсутствие оценок — «Пока мало оценок», не скрытие свежего фильма. Анонсы/недоступные релизы — отдельный явно подписанный раздел, не «Можно смотреть».

Не требовать полного отсутствия повторов: один релиз может заслуженно быть в нескольких местах, но ограничить повторы между соседними полками и повторы одной франшизы. Если данных мало — уменьшить полку/показать объяснение, не маскировать пустоту случайным старым кино. Сохранить удобство телефона, клавиатуры, TV-пульта и понятные сенсорные кнопки; не переписывать все клиенты одним этапом.

## Рекомендации

Начать с объяснимой модели без отдельного ML-сервиса. Отделить генерацию кандидатов от ранжирования, свежести, разнообразия и исключений.

Продумать:
- новый пользователь без истории и пользователь без входа;
- сигналы из избранного, завершённых просмотров, явных предпочтений, скрытий и «не интересно»;
- короткое случайное открытие и проверка плеера не считаются любовью к жанру;
- личный просмотр не подменяется вкусами всех участников совместных комнат;
- рекомендации для пары — отдельный выбранный контекст, только по доступным участникам данным и согласию;
- просмотренное скрывать/понижать с возможностью пересмотреть; незавершённое оставлять в «Продолжить»;
- штраф за однообразие, разумная доля новых/неизвестных карточек и ограничение франшиз;
- учёт давности интересов, небольшое исследование нового, без полной случайной перестановки при каждом refresh;
- честные причины: «Похоже на…», «Из избранного жанра», «Недавно стало доступно». Не писать «На основе вашей истории», если использован общий список.

Определить начальные веса/ограничения как проверяемую гипотезу. Не обещать качество по самому числу карточек или высокому рейтингу. Оценить примеры до/после на фиксированных профилях, отдельно свежесть, разнообразие, доступность и полезность. Не вводить внешнюю аналитику/передачу истории без согласования.

## Архитектура и обновления

Предложить минимальное расширение текущего Python/SQLite/vanilla JS, а не новый стек. Зафиксировать контракт API полок/полных списков, область аккаунта/контекста, порядок, версию данных, признаки устаревания и причины подбора. Серверные фильтры должны применяться до LIMIT, а не к уже обрезанной клиентской странице.

Для импорта нужны идемпотентность, перекрытие временных окон, дедупликация, корректный обход страниц, сохранение watermark только после успешной записи, восстановление после сбоя, уважение лимитов API и атомарная публикация индекса. Не заменять успешные данные пустым/частичным ответом провайдера. Не прятать карточку навсегда после одного timeout; сохранять причину и повторную проверку. Повторный backfill не должен заполнять полку «Добавлено сегодня».

Для новых серий нужен подтверждённый номер/дата/источник события. Если источник не даёт этих данных, показать ограничение, не придумывать точный график. Уведомления пользователю не включать самовольно.

Операционный минимум: последнее успешное обновление каждого источника, отставание, создано/изменено/отброшено с причинами, ошибки/429, курсор, версия и время индекса, длительность запросов. Диагностика не должна раскрывать токены, историю других аккаунтов и приватные данные.

## Отдельный дефект: каталог иногда не загружается

Пользователь сообщил «Не удалось загрузить каталог, проверь подключение и попробуй ещё раз». Не смешивать этот дефект с ранжированием. Сначала зафиксировать URL/устройство/сеть и фактический неудачный запрос: TLS/авторизация/timeout/API/JSON/индекс/PWA. HTTP 401 не называть пустым каталогом; недоступность сети не изображать отсутствием новинок. Дать retry, понятную ошибку и возможность показать последнюю успешную подборку с явной давностью; не кэшировать персональную историю для другого аккаунта. Не ослаблять Basic/viewer-защиту ради исправления.

## Этапы и приёмка

1. Read-only диагностика с примерами и подтверждёнными причинами. Различить локальный и серверный код/данные.
2. Согласованная схема дат/доступности и правила полок, ревью миграции и приватности.
3. Починка импорта/индекса и наблюдаемости на небольшом наборе, затем контролируемое восстановление пропусков.
4. API свежих полок и объяснимое ранжирование; тесты, фиксированное время и профили.
5. Локальный макет главной/каталога, UX-ревью, сравнение до/после и правки.
6. Контролируемая выкладка по отдельному указанию, бэкап, откат и наблюдение после обновления.

Обязательные сценарии: свежий фильм с нулём голосов виден; будущий релиз не выдан за доступный; старый недавно добавленный фильм не выдан за премьеру; новая серия старого сериала попадает в свою полку; обновление постера не освежает релиз; повторный импорт/перезапуск не меняют first_seen; сортировка одинакова на главной и полном списке; ошибка одного источника не обнуляет каталог; дата отсутствует/частичная/будущая обработана явно; граница года и часового пояса; старый PWA; плохая сеть; два аккаунта с разной историей и совместный контекст без утечки.
